## 4. The vacuous test the mutation check found

`TestEndToEndAdaptiveRun::test_a_dataset_with_a_near_random_target_produces_a_reflection_step`
**passed with reflection entirely disabled.** Its assertions sat inside
`if "OrchestratorAgent" in agent_names:` — when nothing fires, the branch never
runs and the test goes green. The name promised a reflection step was produced;
nothing asserted one was.

It was a deliberate trade against flake (GradientBoosting can overfit noise at
small n and score above the trust threshold), but the result was that the only
end-to-end test of the adaptive loop could not fail.

**Fixed by changing the trigger, not the assertions.** Target missingness is
arithmetic over a column, so a 50%-null target is below
`LOW_TARGET_COMPLETENESS_PCT` by construction — deterministic in a way that
judging a model's fit on noise is not. The test now asserts unconditionally that
a reflect step exists, that it names the real column, and that the decision
reaches `RecommendationAgent` rather than only being logged.

Re-ran the mutation: **6 failures → 7.** The new test is now one of them.

This is the third vacuous-test near-miss on this project. The pattern each time
is the same: an assertion that can be skipped rather than one that can be wrong.

## 5. The substring coupling between two agents

`RecommendationAgent` dropped the untrusted attribution pattern by matching the
literal `"' contributes most to predicting"`, against a sentence built 300 lines
away in `MiningAgent._build_patterns`. Two copies of one string, in two files,
with nothing holding them together.

The failure mode is quiet: change the wording in Mining, and the filter stops
filtering while every existing test stays green — because all three tests of
that filter **hand-write the pattern as a literal**, so they test the filter
against a string Mining no longer produces.

Confirmed it rather than assuming: drifting Mining's wording to "is the dominant
predictor of" left all 22 recommendation tests passing while an untrusted
attribution reached the reader as a top finding.

**Fix, in two parts.**

`ATTRIBUTION_PATTERN_MARKER` now lives in `mining_agent.py` beside the only code
that produces it, and `recommendation_agent.py` imports it. Producer output is
byte-identical.

And a test that binds the two — `test_the_filter_matches_a_pattern_mining_actually_produced`
asks `MiningAgent` to build the pattern instead of hand-writing it. The first
version of this test was itself vacuous: asserting the old phrase was *absent*
passes trivially once the phrase changes. It now asserts on the **feature name**
carried by the pattern, with a trusted-run control proving the name reaches the
reader when the filter is off.

Verified by changing the constant's value alone: the filter test passes (both
sides moved together) while `test_feature_attribution.py`'s literal assertions
fail — which is the intended division. The constant makes the coupling
structural; the test literals pin the user-visible sentence, so changing the
wording fails tests named about phrasing rather than silently altering what
readers see.

## 8. A run with no dataset returned a full report

Found by Sarthak while testing: ask a question, select no sample, upload
nothing — and a complete five-recommendation report comes back. Reproduced at
the API: `POST /analysis/run` with a goal and nothing else returned **HTTP 200**.

```
IngestionAgent       error    No data source provided to IngestionAgent.
MiningAgent          success  No ingested dataset available — profiling skipped.
VisualizationAgent   success  No mining output or dataset available — visualization skipped.
RecommendationAgent  success  Produced 5 grounded recommendation(s).
```

Four reasonable decisions compounding into one wrong outcome:

1. **Nothing required a dataset.** `file` and `dataset_id` are both optional in
   the router, and `orchestrator_service.run` was `if file … elif dataset_id …`
   **with no else** — `data["source"]` simply never got set. The UI didn't gate
   it either; the submit button checked only `goal.trim().length < 5`.
2. **A failed step doesn't stop the run.** The orchestrator catches per-agent
   exceptions so one agent can't crash the pipeline — deliberate — but "don't
   crash" was implemented as "record it and continue to the next planned step".
   There is no notion of a failure that should abort.
3. **The next two agents succeed at doing nothing.** MiningAgent returns
   `_empty_result(...)` rather than raising, so the orchestrator stamps it
   `success`. Same for Visualization. Two green checkmarks for skipping the job.
4. **RecommendationAgent never needed the data.** It is RAG keyed on the goal
   text. With no patterns, the "fill remaining slots with a broad goal-only
   retrieval" branch fills all five. That path is real and stays — it is what
   the follow-up chat uses for dataset-free methodology questions.

The result is genuine, correctly-cited knowledge-base content answering *"what
does the literature say about churn prediction"*, rendered in the same shell as
an analysis of the user's data.

### The second bug, found by writing the test

A test for `dataset_id` pointing at nothing was written on the theory that it
was the same hole. It was worse: `resolved_dataset_id` kept the unresolvable id,
and persisting the run hit a **`ForeignKeyViolationError`** — a 500 from a
request that should have been a 422. Would not have been found by reasoning
about the first bug alone.

### Fix

One guard in the service — `if "source" not in data: raise
MissingDataSourceError(...)` — covering both routes to the same state. Its own
exception type, because the routers must tell a caller's mistake (422, or a
WebSocket bad-request close) from a pipeline failure (500); a bare `ValueError`
would be swallowed by the existing `except Exception` and reported as ours. The
WebSocket path gets the same treatment, since it also accepts a bare
`dataset_id`. The UI now disables Run and says which input is missing, but the
API check is the real guard — the button is not the only way in.

### What the existing tests had been encoding

Four tests broke, and every one was asserting the buggy behaviour as normal:

- Three `TestHistory` tests created runs **with no dataset at all**, because it
  was convenient and legal. They are about history and ownership; they now
  upload a file, which is fixture rather than subject.
- `test_dataset_from_another_user_is_not_reusable` and the streaming
  equivalent asserted that a cross-user `dataset_id` "silently gets no source".
  The security property is unchanged — B still cannot distinguish "not yours"
  from "no such dataset", and gets no report either way — but the mechanism is
  now a refusal. Both tests were rewritten to assert the refusal **and** that
  none of the owner's column names or values appear in any frame, which is the
  property they existed to protect and only implied before.
