## 2. Bugs found, and what each one teaches

### 2.1 The Dockerfile shipped a silent fallback (`54ad539`)

`pip install ".[dev]" 2>/dev/null || pip install <hardcoded list>` — and the list had drifted **eight
packages** behind `pyproject.toml`: scikit-learn, shap, reportlab, pdfplumber, duckdb, authlib,
itsdangerous, psycopg2-binary. With stderr discarded, a failed resolution produced an image that
**built cleanly and died at runtime** with nothing in the log. No scikit-learn means no M3 at all.

Removed. A build that fails loudly beats an image that lies about being complete.

### 2.2 The image carried 2.8 GB of CUDA it could never use (`54ad539`)

`sentence-transformers` → `torch`, and PyPI resolution on linux/arm64 now drags in the whole NVIDIA
stack: cublas 543 MB, cudnn 445 MB, cusolver, cusparselt, nccl, triton — 15 wheels. Into a container
with no GPU. Embeddings here are CPU-only by design.

Pinned `torch` from PyTorch's CPU index. **9.87 GB → 3.5 GB, 15 CUDA wheels → 0.** This was also the
root cause of the disk incident in §3: those wheels were re-cached on every build.

### 2.3 `GEMINI_API_KEY` never reached the container (`e132cfb`)

Compose forwarded `OPENAI_API_KEY` and `ANTHROPIC_API_KEY` — neither of which any code reads — but
not the key the project actually uses. So **all three LLM features worked from the host and silently
degraded inside Docker.**

Silently is the whole problem. Every call site guards on `is_configured` and falls back, which is
right for a *missing key* and is exactly what hides a *missing forward*. Nothing looks broken. A
demo from `docker compose up` simply would not have had the AI features.

> Only visible by running the E2E suite against the **containers** rather than the host: 33/34 vs
> 34/34, the single delta being the Gemini path.

### 2.4 Export filenames never reached the browser (`eabb256`)

The frontend reads `Content-Disposition` to name a download. A browser cannot read a response header
cross-origin unless the server exposes it, and `CORSMiddleware` had no `expose_headers` —
`allow_headers=["*"]` governs *request* headers, which is the easy thing to misread.

Every export saved as `download`. Worst hit: the BibTeX bundle, which arrived with **no extension**,
because Chrome infers one from MIME type and does not know `application/x-bibtex`. The one export
whose entire purpose is to be opened by another tool was the one that would not open.

### 2.5 The default view led with a meaningless chart (`eabb256`)

`_categorical_bar_specs` picked columns in dataset order, so on an uploaded CSV — where dates are
text and therefore typed *categorical* — the reporting view led with **"Top values in 'order_date'":
five unique timestamps, each with a count of 1.**

Same root cause as the `grouped_bar` fix on 17 Aug, but in the older builder, which had no guard. Now
skips the time axis and any column more than half distinct. Counting occurrences only means
something when values repeat.

### 2.6 Pairplot panels collapsed under outliers (`eabb256`)

Min-max scaling let three planted extremes own the axis, squashing 400 real points onto a flat line —
a panel that renders and shows nothing. Percentile-scaled (2nd–98th) with out-of-range points clamped
to the edge rather than dropped, so the panel never misstates the observation count. Same reasoning
as the Tukey scaling already in `BoxPlot`.

## 3. The disk incident — worth reading before it repeats

The 17 Aug build failed at `exporting to image` with an I/O error. Cause: **the disk was 100% full,
163 MB free.** Filling mid-write corrupted containerd's blob store, and Docker Desktop crashed.

It then **would not restart** — because three orphaned `com.docker.backend` processes still held the
sockets, so Docker Desktop believed it was already running and the CLI hung on a dead socket.
Killing them fixed it; the backend came up in 6 seconds.

**~50 GB recovered:**

| Source | Freed |
|---|---|
| Docker build cache (`builder prune -af`) — 49 GB across 62 entries | **33 GB** |
| Chrome caches + on-device AI models (`OptGuideOnDeviceModel` alone was 4 GB) | **10 GB** |
| pip / HF / uv / playwright / installer leftovers | **7 GB** |

`Docker.raw` auto-compacted 63 GB → 18 GB afterwards; its 228 GB apparent size is a sparse ceiling,
not consumption.

> **Two lessons.** The build cache was mostly the CUDA wheels from §2.2 — fixing that fixes the
> recurrence. And *the database lives inside Docker* (`postgres-data` volume), so a "reset Docker
> Desktop" would have destroyed it. It survived; it is now also dumped to `~/mage-db-backup.sql`.

## 5. Standing method note

Four of the six bugs were invisible to a green suite. The pattern in every case: **the test and the
deployment disagreed about the environment.** Hand-built fixtures have parsed dtypes, uploaded CSVs
have text. The host has an `.env`, the container has whatever compose forwards. Same-origin fetch
sees every header, cross-origin sees three.

Run the thing, in the way it will actually be run. Then read the output rather than the log — on
17 Aug the build log said `Successfully built` while the image was three weeks stale, and only
`docker run … import shap` caught it.
